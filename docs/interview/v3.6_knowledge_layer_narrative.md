# v3.6 知识层基础设施 — 面试叙事脚本

## 中文版（3-5 分钟）

### 背景铺垫（30 秒）

WealthPilot 在 v3.5 之前已经实现了完整的 Multi-Agent PEER 架构——Planning/Executing/Expressing/Reviewing 四个 Agent 协作，12 个 Skills 覆盖从意图识别到投资决策的全流程。但在实际使用中，我发现了一个结构性缺失。

### 核心矛盾定义（30 秒）

用户在系统里沉淀了大量定性知识——比如投研对话的完整推理过程、投资纪律中"港股回调时分批建仓"这种定性偏好、"长期主义不追热点"这类投资哲学。但系统只消费了结构化字段（标的代码、目标价、仓位上限百分比），大量语义信息被丢弃。等于说用户给了系统 100% 的信息，系统只用了 20%。

### 设计方案（1 分钟）

我设计了 File-as-Source-of-Truth 架构：Markdown 文件是知识真相源，Chroma 向量库是可重建的索引层。这个选择有三个理由：一是人机可读——用户可以用任何编辑器修改知识，不依赖 UI；二是 Git 友好——知识变更有版本历史；三是可重建性——向量库坏了，从 MD 文件重建就行。

在 Skill 层面，我评估了四种检索 Skill 的拆分方案——单 Skill 多参数、双 Skill 语义二分、按类型三拆、以及删旧建新。最终选择了方案 B：保留现有的 `wp-fetch-research`（负责标的相关投研）+ 新增 `wp-retrieve-principles`（负责用户原则类知识）。核心理由是"标的知识 vs 用户原则"是投资决策领域的天然语义边界，而不是按数据库表来拆分。

### 技术亮点（1 分钟）

三个值得一提的设计点：

第一，Skill 边界不是按数据表拆，而是按决策语义拆。这个判断来自于一个关键的架构事实——PlanningAgent 99% 用静态 Bundle 选 Skill，不走 LLM 动态选择。所以"Planning 能不能选对 Skill"这个维度的区分度远低于预期，真正重要的是语义是否清晰、维护是否便利。

第二，general 路由改造中的"子意图判断"。Education 路由原本完全跳过数据加载（SKIP），但知识库上线后需要注入配置原则。我用 20 个投资关键词做子意图判断——命中投资关键词的 query 走 RAG 召回，闲聊不触发。简单、可解释、零 LLM 成本。

第三，整个工作流本身。先做现状勘探（7 个维度盘点），再做 Skill 边界理论评估（5 个维度 × 4 个方案），然后分 5 批增量交付。每批严格控制范围，13 个 commits 每个可独立回滚。这种"先勘探后设计、小步验证"的方法论本身是一个工程能力的展示。

### 成果（30 秒）

v3.6 完成后，WealthPilot 从"只能用结构化字段做决策"升级为"结构化字段 + 语义知识双轨决策"。投研观点的完整推理过程、纪律手册的定性偏好、配置方法论——这些此前"给人看但没参与决策"的内容，现在都通过 RAG 进入了 LLM 的决策上下文，而且每条引用都可追溯来源。

### 演进规划（30 秒）

v3.6.1 补 UI（投资风格输入框、时效标签可编辑），v3.6.2 启用时效衰减打分和 LLM rerank 提升召回质量。更远期，v4.0 计划引入 Mem0 做用户偏好的更高维度记忆，知识库是那个方向的基础设施。

## English Version (3-5 minutes)

### Context (30s)

WealthPilot had a complete Multi-Agent PEER architecture by v3.5 — four specialized Agents orchestrating 12 Skills for investment decisions. But I identified a structural gap during actual usage.

### The Core Problem (30s)

Users were depositing rich qualitative knowledge — full reasoning from research conversations, qualitative preferences like "scale into HK positions during pullbacks," investment philosophies like "long-term value, no leverage." But the system only consumed structured fields — ticker symbols, target prices, position percentages. Essentially, users gave the system 100% of the information, but it only used 20%.

### Design Approach (1 min)

I designed a File-as-Source-of-Truth architecture: Markdown files are the single source of truth, Chroma vector DB is a rebuildable index layer. Three reasons: human-machine readable (edit knowledge with any editor), Git-friendly (version history for knowledge evolution), and rebuildable (vector DB corruption? Just rebuild from MD files).

For Skill boundaries, I evaluated four splitting strategies and chose Plan B: keep existing `wp-fetch-research` (asset-specific research) + add `wp-retrieve-principles` (user principles). The key insight is that "asset knowledge vs. user principles" is a natural semantic boundary in investment decisions — not a database-table-driven split.

### Technical Highlights (1 min)

Three design decisions worth discussing:

First, Skill boundaries based on decision semantics, not data schemas. This came from a critical architectural discovery — PlanningAgent uses static bundles 99% of the time, not LLM-based selection. So "can Planning pick the right Skill?" has low discriminating power. What matters is semantic clarity and maintainability.

Second, sub-intent detection in the general route. The Education route previously skipped all data loading. With the knowledge base, it needs allocation principles injected. I used 20 investment keywords for sub-intent detection — investment queries trigger RAG, casual chat doesn't. Simple, explainable, zero LLM cost.

Third, the delivery methodology itself. Exploration first (7-dimension baseline audit), then design evaluation (5 dimensions x 4 candidate plans), then incremental delivery in 5 batches. 13 commits, each independently revertible. This "explore-then-design, verify-in-small-steps" approach is itself a demonstration of engineering discipline.

### Results (30s)

After v3.6, WealthPilot upgraded from "structured-fields-only decisions" to "structured + semantic dual-track decisions." Full research reasoning, qualitative discipline preferences, allocation methodologies — content that was previously "visible to humans but invisible to AI" — now enters the LLM decision context via RAG, with every citation traceable to its source file.

### Roadmap (30s)

v3.6.1 adds UI (investment style input, editable time sensitivity tags). v3.6.2 enables time-decay scoring and LLM reranking for retrieval quality. Longer term, v4.0 plans Mem0 integration for higher-dimensional user preference memory — the knowledge base is the infrastructure foundation for that direction.
