## 0. 一句话定位

把 v3.7 引入的"日志显性化"升级为**可分析的结构化对账层**：每次 ExecutingAgent 执行结束后，如实记录"声明该跑的 Executing Skill"与"实际跑的 Executing Skill"之间的差异，为 v3.8.2 的分阶段 manifest 设计提供一手数据。

**ExecutingAgent 继续按 route 硬编码 if/elif 跑，控制流零改动。对账层是纯旁路观测，不驱动任何执行。**

## 1. 背景：为什么 v3.8.1 从"驱动"重定义为"对账"

### 1.1 原计划与勘探发现的冲突

handoff 原计划：让 ExecutingAgent 读 `selected_skills` 驱动执行，替换 route 硬编码。

两轮勘探推翻了这个前提的可行性。`selected_skills`（即 `_SKILL_BUNDLES_BY_ROUTE`）**根本不是 Executing 阶段的执行清单**，而是一份混合了三个 PEER 阶段 + 幽灵 Skill 的标称配置。以 `position_single` 为例（清单 8 项）：

| 清单 Skill | 实际归属（勘探 C5） | ExecutingAgent 实际行为 |
|---|---|---|
| wp-fetch-holdings | Executing（内嵌） | 不单独 invoke，被 `wp-load-context` 内的 `data_loader.load()` 吞掉 |
| wp-fetch-research | Executing（内嵌） | 同上 |
| wp-retrieve-principles | Executing（内嵌） | 同上（general 路由则直接调 KnowledgeStore） |
| wp-check-discipline | Executing | ✅ 真 invoke（L244 并行 + L427 新建仓） |
| wp-generate-signals | Executing | ✅ 真 invoke（L250 并行） |
| wp-reasoning | **Expressing** | 不在 Executing，ExpressingAgent 直接 import llm_engine 调 |
| wp-citation-rules | **幽灵** | 生产代码无 invoke 点，内容硬编码进 prompt 常量 |
| wp-output-validator | **Reviewing** | 不在 Executing，ReviewingAgent 直接 import 调 |

同时，ExecutingAgent 真正跑了、但**完全不在清单里**的：`wp-load-context`（真正的编排入口）、4 个市场数据服务（futu/av/tiger，带条件 + ThreadPoolExecutor 并行，并往 `invoked_skills` 追加 4 个伪 Skill 名）。

**结论**：清单与执行在颗粒度、阶段归属、调用方式三个维度上全部错位。"让 ExecutingAgent 照清单跑"不是一次行为保持的重构，而是要先重新定义清单语义——而清单语义的重新定义恰好依赖 v3.8.2（分阶段结构）。强行在 v3.8.1 做会产出一个行为必变的伪重构，违反"前端零感知"硬约束。

### 1.2 主路决策（已与 PM 对齐）

v3.8.1 重定义为**对账层**：
1. 风险最低，符合"前端零感知"硬约束
2. 符合"一个版本一件事"工程纪律
3. 产出的对账数据是 v3.8.2 设计的真实依据，比凭空设计 manifest 靠谱

### 1.3 主路安全性的勘探支撑

补充勘探任务 B 全仓 grep 确认：**无行为性消费点**。`selected_skills` 被赋值后，只在日志输出（3 处）、测试断言（4 处）、注释文档（14 处）中出现。ExecutingAgent / ExpressingAgent / ReviewingAgent / decision_service_v3 **均不读取**它驱动行为。因此"对账层是纯旁路、不可能影响现有行为"这一假设成立。

## 3. 设计

### 3.1 静态常量：Skill → PEER 阶段归属表（诊断用，非最终架构真相）

# backend/agents/observed_skill_phase_map.py  (新建文件)
#
# Diagnostic-only mapping for v3.8.1 reconciliation.

### 3.2 对账数据结构与算法

```python
# backend/agents/skill_reconcile.py  (新建文件)

from dataclasses import dataclass, field
from .observed_skill_phase_map import SKILL_PHASE, PSEUDO_SKILLS

@dataclass
class ReconcileReport:
    route: str
    declared_exec: list[str] = field(default_factory=list)        # 分母:声明归属 executing
    invoked_exec: list[str] = field(default_factory=list)         # 分子:实跑归属 executing
    matched: list[str] = field(default_factory=list)              # 声明且实跑
    declared_not_invoked: list[str] = field(default_factory=list) # 声明未实跑
    invoked_not_declared: list[str] = field(default_factory=list) # 实跑未声明
    pseudo_observed: list[str] = field(default_factory=list)      # 观测到的伪 Skill
    unknown_declared: list[str] = field(default_factory=list)     # 清单里 map 未覆盖的 wp-*
    unknown_invoked: list[str] = field(default_factory=list)      # 实跑里 map 未覆盖的 wp-*
    is_consistent: bool = True   # 仅基于 executing 阶段 diff
    has_unknown: bool = False    # 出现映射表未覆盖的 wp-* skill


def reconcile_executing_skills(route, selected_skills, invoked_skills) -> ReconcileReport:
    """纯函数。只比对 Executing 阶段。不修改任何入参。对 None 入参鲁棒。"""
    # None 防御:绝不让对账层因入参为 None 而崩溃(第一原则:不影响业务流)
    selected_skills = selected_skills or []
    invoked_skills = invoked_skills or []
    route = route or ""

    # 分母:声明且归属 executing
    declared_exec = {s for s in selected_skills if SKILL_PHASE.get(s) == "executing"}

    invoked_set = set(invoked_skills)
    pseudo = invoked_set & PSEUDO_SKILLS
    invoked_real = invoked_set - PSEUDO_SKILLS
    # 分子:实跑且归属 executing
    invoked_exec = {s for s in invoked_real if SKILL_PHASE.get(s) == "executing"}

    # unknown 兜底:出现在清单/实跑里、但映射表完全没覆盖的 wp-* skill
    # (绝不静默吞掉 —— 对账层的本职就是发现契约差异)
    unknown_declared = {s for s in selected_skills if s.startswith("wp-") and s not in SKILL_PHASE}
    unknown_invoked  = {s for s in invoked_real   if s.startswith("wp-") and s not in SKILL_PHASE}

    matched = declared_exec & invoked_exec
    declared_not_invoked = declared_exec - invoked_exec
    invoked_not_declared = invoked_exec - declared_exec

    is_consistent = (not declared_not_invoked) and (not invoked_not_declared)
    has_unknown = bool(unknown_declared or unknown_invoked)

    return ReconcileReport(
        route=route,
        declared_exec=sorted(declared_exec),
        invoked_exec=sorted(invoked_exec),
        matched=sorted(matched),
        declared_not_invoked=sorted(declared_not_invoked),
        invoked_not_declared=sorted(invoked_not_declared),
        pseudo_observed=sorted(pseudo),
        unknown_declared=sorted(unknown_declared),
        unknown_invoked=sorted(unknown_invoked),
        is_consistent=is_consistent,
        has_unknown=has_unknown,
    )
```

设计要点：
- **纯函数，无副作用**。便于单测，且保证不可能波及主流程。
- **只比对 Executing 阶段**。reasoning（Expressing）、output-validator（Reviewing）、各幽灵 Skill 自动从分母排除。
- **伪 Skill 单独归类**到 `pseudo_observed`，不参与 matched/diff 计算，但留痕。
- **unknown 绝不静默吞掉**。`SKILL_PHASE.get(s)` 对未覆盖项返回 `None` 会被排除出 executing 集，但这些项会被 `unknown_*` 显性捕获。`is_consistent` 只反映 executing diff；`has_unknown` 是独立信号。

### 3.3 挂点：ExecutingAgent.run() 末尾（一致/不一致都打）

在 `run()` 的 `return out` 之前插入调用点。**只读 `out.invoked_skills` 和 `planning_output`，不写 `out` 的任何字段。**

```python
# executing_agent.py run() 末尾,return out 之前
#
# 整块包 try/except:对账层是旁路观测,任何异常(reconcile / json.dumps /
# import / 意外对象)都【只记录、不中断】,绝不影响 return out。
# 限定 except Exception —— 不吞 BaseException(KeyboardInterrupt / SystemExit)。
try:
    report = reconcile_executing_skills(
        route=planning_output.route,
        selected_skills=planning_output.selected_skills,
        invoked_skills=out.invoked_skills,
    )
    payload = {
        "route": report.route,
        "declared_exec": report.declared_exec,
        "invoked_exec": report.invoked_exec,
        "matched": report.matched,
        "declared_not_invoked": report.declared_not_invoked,
        "invoked_not_declared": report.invoked_not_declared,
        "pseudo_observed": report.pseudo_observed,
        "unknown_declared": report.unknown_declared,
        "unknown_invoked": report.unknown_invoked,
        "is_consistent": report.is_consistent,
        "has_unknown": report.has_unknown,
    }
    line = "[SKILL_RECONCILE] " + json.dumps(payload, ensure_ascii=False)
    # 一致且无 unknown → info(低噪声);不一致或出现 unknown → warning(需关注)
    if report.is_consistent and not report.has_unknown:
        logger.info(line)
    else:
        logger.warning(line)
except Exception:
    logger.exception("[SKILL_RECONCILE_ERROR] reconciliation failed, ignored")

return out  # ← 对账层无论成功失败,都不改变这一行的返回值
```

> **零行为风险红线（硬约束）**：对账层的任何异常都不得影响 ExecutingAgent 的返回结果。`return out` 的值在挂接对账层前后必须完全一致。

- 固定 prefix `[SKILL_RECONCILE]` + 单行 JSON。**所有进入 ExecutingAgent 的 route 都打**，保证 v3.8.2 拿到完整样本（含一致/空/异常场景），不会把"无差异"和"无记录"混淆。
- level 区分控制噪声：一致且无 unknown 用 info；不一致或 unknown 用 warning。
- `has_unknown` 单独成字段：position 路由因已知稳定差异会恒 warning，分析脚本可专门 `filter has_unknown==true` 揪出"映射表过时"信号，不被淹没。

> **挂点边界提醒**：clarify / low_confidence 路由在 decision_service_v3 层已短路 return，**根本不进 ExecutingAgent**（勘探任务 5）。因此对账层不会被这两个 route 触发，无需为它们设计。

## 6. 验收标准

### 6.1 硬标准（不可妥协）

1. **18 个 M5 用例 100% 通过。** 对用户可见响应做如下校验（而非字节级 diff）：
   - SSE 事件类型、事件顺序、字段 schema 保持不变
   - explain API schema 保持不变
   - 前端依赖字段保持不变
   - 自然语言内容**不做字节级 diff**，仅抽查语义与决策类型无异常（链路含 LLM，自然语言/时间戳/trace id 本就非确定）
   - 若有 mock / fixture 回放模式，可对 deterministic payload 做严格 diff
2. 对账报告**只出现在日志**，grep 确认 `ExecutionOutput` / SSE / API response 中无 ReconcileReport 痕迹。

### 6.2 对账正确性标准

3. 逐 route 核对对账日志输出与第 4 节"预期稳定差异基线"一致。
4. **防误判**（吸取 v3.6.5 关键词漏检教训）：正确性核对**必须比对差异集合的具体元素**，不能只看"warning 有没有打"或"数量对不对"。集合内容逐个 Skill 名核对。
5. 确认所有 route 的 `has_unknown == false`。若为 true，说明 `observed_skill_phase_map` 漏项，需补全后重跑。

### 6.3 验收脚本化（控制 PM 成本）

6. 让 Claude Code 跑批量后端调用（覆盖 position_single / position_multi / portfolio / general 各 2-3 个，共约 12 次），grep `[SKILL_RECONCILE]` 行，逐行 `json.loads` 解析，出一份对账报告（`docs/v3.8.1_reconcile_validation_report.md`）：
   - 按 `is_consistent` 分组汇总（一致组 / 不一致组），再按 route 二级分组
   - 单列 `has_unknown == true` 的行（预期为空）
   - 每个 route 给出实际差异集合 vs 第 4 节预期基线的逐元素对比
7. PM 只看报告摘要 + 抽审 2-3 个完整日志行。
8. 浏览器只验最关键 UI（position 决策渲染）未变化，不需每个用例都开。

### 6.4 环境提醒（Mac 本地）

- 脚本访问 localhost 必须加 `NO_PROXY=127.0.0.1,localhost`（Clash Verge 7897 会拦）
- VPN + OpenAI 链路单次决策可能 >60s，脚本 timeout 放宽

## 8. 不打 feature flag 的理由

原计划建议双轨 + flag，前提是"改控制流、需要可切换回退"。重定义为对账层后，控制流零改动，没有可切换的两条路径，flag 无意义。对账层若出问题，最坏情况是日志多打/少打一条，不影响任何用户可见行为——直接改日志级别或摘除调用点即可，无需 flag 保护。

## 9. 对 v3.8.2 的交接价值

v3.8.1 产出的对账日志，是 v3.8.2 设计"分阶段 manifest"的一手依据：
- `declared_not_invoked` 暴露了"清单声明但被 load-context 吞掉"的 Skill —— v3.8.2 设计 manifest 时需决定：是把这些显式建模为 load-context 的展开，还是从 Executing 清单移除
- `invoked_not_declared`（稳定为 load-context）暴露了"真正的编排入口缺席于清单" —— v3.8.2 的 Executing manifest 必须把 load-context 列为一等公民
- `declared_exec` / `invoked_exec` 提供完整分子分母，便于直接还原上下文
- `pseudo_observed` 暴露了 4 个市场服务的伪 Skill 现状 —— v3.8.2 需决定它们是否升格为真 Skill
- `has_unknown` / `unknown_*` 作为映射表健康度信号，提醒后续维护

> 注：`observed_skill_phase_map` 是诊断观测表，**不是** v3.8.2 manifest 的权威 schema。v3.8.2 应基于本版对账积累的真实数据重新设计 manifest 结构，而非直接沿用本表。
