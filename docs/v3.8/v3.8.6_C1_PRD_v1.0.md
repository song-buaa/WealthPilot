## 2. 关键勘探事实

### 2.1 接通点：仅一处（任务 A1 + C2）

`reviewing_agent.py` `_run_hard_validation` 内 **L196-199 唯一一处**调 validate_decision_output：
```python
vr = validate_decision_output(result=llm_result, intent_type=intent_type)
```
全关键字参数，无位置参数，discipline_violations 用默认 None。

### 2.2 经 invoke_skill 调到的是同一个函数（任务 B2/B3）

wp-output-validator 是 validation 类型，entry_point = `backend.graph.decision_validator:validate_decision_output`，
SkillsLoader._invoke_validation 动态 import 后 `func(**params)` —— 调到的就是同一个函数。
`invoke_skill("wp-output-validator", result=llm_result, intent_type=intent_type)` 与现在的直连
**完全等价**：参数同、返回类型同（ValidationResult）、result 传对象引用无需序列化。**无 C0 厚参数问题。**

### 2.3 不碰 general、不碰对账层（任务 C3/D1）

- validator 实际只对 **position_single / portfolio** 生效。general 走到 Reviewing 时
  llm_result 通常为 None（chat 返回纯 str），L183-186 直接 return、不调 validator。
  → **C1 自动避开 general 不可信基线。**
- 对账层只看 Executing 阶段的 invoked_skills，**看不到 Reviewing 的 invoke**（ReviewOutput 无
  invoked_skills 字段）。→ **C1 接通后 position/portfolio 的对账可信基线一个字不变。**

### 2.4 验收抓手：SSE 可观测输出（任务 D2）

对账验不了 C1（看不到 Reviewing），改用 validator 影响的可观测输出验"双轨等价"：
1. `done` 事件 payload 里的 `validator` 字段（decision_service_v3.py L690-697）：`{passed, action, failures}`
2. action==retry 时的 `validator_warning` SSE 事件（L270-274）：含 failed_rules

## 3. C1 设计

### 3.1 feature flag

```python
# flag 名:WP_USE_SKILL_OUTPUT_VALIDATOR
# 一个 Skill 一个 flag,便于逐个接通/独立回退
# 默认关(未设或 != "1" 都视为关)→ 走老直连路径
import os
def _use_skill_output_validator() -> bool:
    return os.environ.get("WP_USE_SKILL_OUTPUT_VALIDATOR", "") == "1"
```

### 3.2 双轨改造（reviewing_agent.py L196-199 唯一一处）

```python
# 改造前:
vr = validate_decision_output(result=llm_result, intent_type=intent_type)

# 改造后(双轨):
if _use_skill_output_validator():
    from backend.skills import invoke_skill
    vr = invoke_skill(
        "wp-output-validator",
        result=llm_result,
        intent_type=intent_type,
    )
else:
    from backend.graph.decision_validator import validate_decision_output
    vr = validate_decision_output(result=llm_result, intent_type=intent_type)
```

要点：
- 两条路径返回的都是同一个 ValidationResult，后续 `vr.passed` / `vr.failures` 等用法不变。
- 已有的 try/except（L195-203）继续包住两条路径，异常处理不变。
- L183-186 的 `llm_result is None` 前置判断（general 短路）保持不动，两轨都在它之后。

### 3.3 C1 不做的事（实施 prompt 顶部置顶）

1. **不删老的直连路径** —— 双轨保留，旧路径作 fallback，待 C7 统一删。
2. **不动 general 相关任何代码** —— general 基线不可信问题归 C2，C1 不碰。
3. **不动对账层 / observed_skill_phase_map / manifest 两张表**。
4. **不动前端 / SSE 事件格式 / API schema / ExecutionOutput / ReviewOutput 字段**。
5. **不改 validate_decision_output 函数本身**（两轨调的是同一个它）。
6. **不动 ReviewingAgent 的其他逻辑**（L2 LLM 评分、action 决策等）—— 只包 L196 那一处。
7. **flag 默认关**，不得默认开。
8. **不修 C2 待办里的 user_query bug / 历史基线** —— 那是 C2 的活。

## 4. 验收策略

### 4.1 核心：双轨等价（flag on vs off 输出逐字段一致）

C1 第一次改 Agent 行为，验收主轴是"新路径与老路径产出的可观测输出完全一致"。
**对账层不参与 C1 验收**（它看不到 Reviewing）—— 这是与前几版的关键区别。

### 4.2 验收清单

1. **单测** test_c1_output_validator_dual_track.py：
   - flag off：reviewing 走直连，验 vr 正常。
   - flag on：reviewing 走 invoke_skill，验 vr 正常、且与 flag off 路径对【同一组输入】
     返回的 ValidationResult 逐字段一致（passed / action / failures / intent_type）。
   - 可用 mock 构造若干 LLMResult/GenericLLMResult 输入，覆盖 passed/retry/fallback 三种 action。
2. **双轨 SSE 对拍（真实请求）**：对一批 position_single / portfolio 请求，分别 flag off / flag on
   各跑一次，从 SSE 抓：
   - done 事件 validator 字段（passed / action / failures）
   - validator_warning 事件（若有）的 failed_rules
   两次逐字段一致。贴并排对比表。
3. **对账不变（旁证）**：flag on 跑 position/portfolio，对账 [SKILL_RECONCILE] 输出仍与
   C0 验收里 Case1-4 的【真实请求基线】一致（验证 C1 没顺手碰到 Executing）。
   注：只比 Case1-4，general 的 Case5/6 基线不可信，不纳入。
4. **M5 回归**：flag off 跑,18/18 与基线一致(注:M5 此前 16/18 的两个 SSE 断连若复现,
   按 C0 同样方式 curl 复核是否网络问题,不算 C1 回归)。
5. **前端零感知**：git diff 确认 contracts / decision_service_v3 / api / frontend 无改动
   （C1 只改 reviewing_agent.py）。
6. **flag 默认关确认**：不设环境变量时，grep + 实跑确认走的是老直连路径。

### 4.3 环境（同前）
