## 0. 一句话定位

把旧 `_SKILL_BUNDLES_BY_ROUTE`（扁平 `dict[str, list[str]]`，混三阶段 + 幽灵 Skill）
的**两个被混淆的职责拆开**：

1. 新增 **SKILL_MANIFEST** —— 忠实描述 Executing + Expressing 两阶段在每种提问下的真实动作；
2. 保留 **LEGACY_SELECTED_SKILLS_BY_ROUTE** —— 原样承接旧 bundle，专供 `PlanningOutput.selected_skills`
   输出，保证与 v3.8.1 逐元素一致。

**v3.8.2 只建表 + 拆职责，系统执行行为完全不变（B 范围），不让任何 Agent 按 manifest 驱动。**

---

## 1. 背景与范围决策

### 1.1 为什么做

v3.8.1 对账层用实测数据证明：旧 bundle 与代码实际执行三维度错位。但旧 bundle 还**兼着一个
活职责**——它被展开成 `selected_skills`，而对账层正依赖这个值工作。所以不能直接把旧 bundle
改忠实，否则 selected_skills 变了、v3.8.1 对账基线全废。

**v3.8.2 的本质是拆职责**：让"忠实描述"和"兼容输出"由两张表分别承担，互不干扰。

### 1.2 范围 = B（已与 PM 对齐）

manifest 覆盖 Executing + Expressing 两阶段，**只描述不驱动**。Reviewing 无 route/intent
分支（勘探 C2），不纳入。C 范围（让 Agent 按 manifest 驱动）留待后续独立版本。

### 1.3 四项已拍板决策（不变）

1. **决策一**：wp-load-context 进 Executing manifest 当一等公民。
2. **决策二（双身份）**：被 load-context 吞的 fetch 类，按"是否在该意图下单独露面"归属。
3. **决策三（粒度）**：manifest 粒度 = route + primary_intent + 关键数据状态。
4. **范围 B**：覆盖 Executing + Expressing。

---

## 2. 关键勘探事实（落表依据）

### 2.1 三个被吞 Skill 的"双身份"（勘探 B2/B3）

`data_loader.load()` 内部完全不走 Skill 机制（B3：8 步全 service/store 直连）。三个 fetch
在 load 内部不是 Skill 形态，是内部步骤；但其中两个在特定意图下会在 ExecutingAgent 层单独露面：

| Skill | load 内部（被吞） | 单独露面的意图 |
|---|---|---|
| wp-fetch-holdings | Step 2，所有路由 | 从不单独露面 → 纯归 load-context |
| wp-fetch-research | Step 7，position/portfolio | portfolio·PortfolioReview（L577 单独 append） |
| wp-retrieve-principles | Step 7b，position/portfolio | general 关键词命中（L596 单独 append；对账 Case 5） |

### 2.2 general 不按子意图拆（补充勘探 E）

GeneralChat 与 Education 在两阶段走完全相同代码路径（Executing 只按关键词命中判断；
Expressing 共用 `_express_general_chat` → `llm_engine.chat`，同模板 general_chat）。
→ manifest 不拆 Chat/Education，只按"关键词命中/不命中"分两种。

### 2.3 新建仓单列行，挂 PositionDecision 下（补充勘探 F）

route/intent 与主干相同（position_single + PositionDecision），但两阶段都有独立代码分支，
区分键 = `loaded.is_new_entry` 数据状态。新建仓 invoked 的 `m8-new-entry-analysis` 与
`wp-check-discipline-partial` 是 **invoked_skills 里的伪标记（append_marker），不是真 Skill**
（v3.8.1 已确认，归入 PSEUDO_SKILLS）。

## 3. 目标结构：双层设计

### 3.1 第一层：SKILL_MANIFEST（忠实描述，新产出）

**职责**：如实描述每种提问情况下 Executing + Expressing 两阶段的真实动作。**不参与
selected_skills 生成。** 全面结构化为对象列表，区分真 Skill 与伪标记。

```python
# backend/agents/skill_manifest.py (新建)
# 忠实描述层。仅用于真实任务分工描述 + 后续架构演进。
# 【不得用于生成 PlanningOutput.selected_skills】—— 那由 LEGACY 表负责。
#
# 每个动作项结构: {"name": str, "kind": str, "impl": str(可选)}
#   kind: "skill"          —— 真 wp-* Skill(走 invoke_skill 或单独 append)
#         "orchestrator"   —— wp-load-context(编排入口,内部吞多个 service 直连)
#         "append_marker"  —— invoked_skills 里的伪标记,非 Skill 协议对象
#   impl: Expressing 项标注背后实际 LLM 函数

def S(name, impl=None):      # 真 Skill 简写
    return {"name": name, "kind": "skill", **({"impl": impl} if impl else {})}
def ORC():                   # 编排入口
    return {"name": "wp-load-context", "kind": "orchestrator"}
def MARK(name):              # 伪标记
    return {"name": name, "kind": "append_marker"}
def REASON(impl):            # Expressing 推理
    return {"name": "wp-reasoning", "kind": "skill", "impl": impl}

SKILL_MANIFEST = {
    "position_single::PositionDecision::main": {
        "executing":  [ORC(), S("wp-check-discipline"), S("wp-generate-signals")],
        "expressing": [REASON("llm_engine.reason")],
    },
    "position_single::PositionDecision::new_entry": {
        "executing":  [ORC(), MARK("m8-new-entry-analysis"), MARK("wp-check-discipline-partial")],
        "expressing": [REASON("llm_engine.reason_new_entry")],
    },
    # position_multi::PositionDecision::main / ::new_entry 同 position_single

    "portfolio::PortfolioReview": {
        "executing":  [ORC(), S("wp-fetch-research")],   # 双身份:此意图下单独露面
        "expressing": [REASON("llm_engine.review_portfolio")],
    },
    "portfolio::AssetAllocation": {
        "executing":  [ORC()],
        "expressing": [REASON("llm_engine.analyze_allocation")],
    },
    "portfolio::PerformanceAnalysis": {
        "executing":  [ORC()],
        "expressing": [REASON("llm_engine.analyze_performance")],
    },

    "general::keyword_hit": {
        "executing":  [S("wp-retrieve-principles")],     # general 不走 load-context(Step 0 核实)
        "expressing": [REASON("llm_engine.chat")],
    },
    "general::keyword_miss": {
        "executing":  [],
        "expressing": [REASON("llm_engine.chat")],
    },

    "clarify":        {"executing": [], "expressing": []},   # 不进 ExecutingAgent
    "low_confidence": {"executing": [], "expressing": []},   # decision_service 层短路
}
```

> **general 的 executing 列是 Step 0 必须核实的开放项**：勘探显示 general 很可能完全不经
> wp-load-context（`_execute_general` 直接处理）。Step 0 核实后据实定。**不放占位符。**

### 3.2 第二层：LEGACY_SELECTED_SKILLS_BY_ROUTE（兼容输出，保持现状）

**职责**：原样保留 v3.8.1 旧 bundle 内容，专供 `PlanningOutput.selected_skills` 生成，
保证输出值与 v3.8.1 逐元素一致。**就是旧 `_SKILL_BUNDLES_BY_ROUTE` 改个名字、内容一字不动。**

**保留旧名 alias 一个版本**（防漏引用导致运行期炸）：
```python
_SKILL_BUNDLES_BY_ROUTE = LEGACY_SELECTED_SKILLS_BY_ROUTE  # deprecated alias, remove in v3.8.3+
```
实施时 grep 全仓确认旧名 `_SKILL_BUNDLES_BY_ROUTE` 只剩此 alias 定义 + 注释，无其他实际引用
（引用都应指向新名或经 alias）。alias 留待 v3.8.3+ 删除。

```python
# 内容 == v3.8.1 的 _SKILL_BUNDLES_BY_ROUTE,逐字不变。
# 仅用于 _select_skills_for_route → PlanningOutput.selected_skills 兼容输出。
LEGACY_SELECTED_SKILLS_BY_ROUTE = {
    "position_single": ["wp-fetch-holdings", "wp-fetch-research", "wp-retrieve-principles",
                        "wp-check-discipline", "wp-generate-signals",
                        "wp-reasoning", "wp-citation-rules", "wp-output-validator"],
    "position_multi":  [ ... 同上 ... ],
    "portfolio":       ["wp-fetch-holdings", "wp-fetch-research", "wp-retrieve-principles",
                        "wp-calc-allocation-deviation", "wp-propose-allocation",
                        "wp-reasoning", "wp-citation-rules", "wp-output-validator"],
    "general":         ["wp-retrieve-principles", "wp-reasoning"],
    "clarify":         [],
}
```

### 3.3 两层关系（关键边界）

- `_select_skills_for_route` / `_llm_augment_skills` / 合并逻辑，**只读 LEGACY 表**，行为与
  v3.8.1 完全一致。
- `SKILL_MANIFEST` 本版**业务运行链路不读取它**。它是纯描述产物，等未来 C 范围版本才会有
  adapter 消费它。**例外**：manifest 自洽单测、覆盖性检查脚本、文档生成脚本可以读取 SKILL_MANIFEST
  （这些不属于业务运行链路）。
- **严禁用 SKILL_MANIFEST 展开生成 selected_skills**，除非未来有专门 adapter 能 100% 还原旧
  bundle（本版不做）。

### 3.4 表的设计原则

1. 被 load-context 吞、从不单独露面的步骤不单列，由 ORC() 代表；只有在该意图下单独 invoke/append
   的才单列（双身份）。
2. 粒度细到代码实际有分支处：portfolio 拆三子意图；position 拆主干/新建仓；general 拆命中/不命中。
   代码无分支处不凭空拆（general 不拆 Chat/Education）。
3. Expressing 项统一 wp-reasoning，但带 impl 标背后函数。
4. 真 Skill / orchestrator / append_marker 三类用 kind 字段严格区分。

## 5. 验收策略

### 5.1 核心：对账层兜底

manifest 改完后，selected_skills 由 LEGACY 表生成、值不变，则 v3.8.1 对账层输出的 6 个 case
差异**必须与 v3.8.1 验收报告逐元素一致**。这是"系统行为零变化"的强证据。

### 5.2 验收清单

1. **selected_skills 不变**：跑 v3.8.1 那批 case，[SKILL_RECONCILE] 输出与
   `docs/v3.8.1_reconcile_validation_report.md` 逐元素一致（六个字段全等）。任一变化即停。
2. **legacy 兼容单测** `test_legacy_selected_skills_compat.py`：断言 LEGACY 表逐 route ==
   v3.8.1 旧 bundle；断言 `_select_skills_for_route` 输出不变。
3. **manifest 忠实性单测** `test_skill_manifest.py`：断言每个意图情况的 executing/expressing
   列与第 3.1 节表一致；断言 kind 字段正确（ORC/append_marker/skill 分类无误）。
4. **M5 回归 18/18**，与 v3.6.5 / v3.8.1 基线一致。
5. **前端零感知**：git diff 确认 contracts / decision_service_v3 / api / frontend 无改动；
   grep 确认两张表都不渗入用户可见层。
6. **manifest 覆盖性检查（非集合相等）**：SKILL_MANIFEST 中每个 kind=="skill" 的 wp-*，
   必须能在 observed_skill_phase_map 或显式例外表中找到归属；但 observed_skill_phase_map 中
   存在、manifest 未单列的 Skill（如 fetch-holdings），只要被 ORC()(wp-load-context) 聚合解释
   覆盖，**不视为矛盾**。不做集合相等检查。
