> **这是什么**：把当前"写死代码 + 大面积绕过 Skill 机制"的实现，改造成"真实代码按
> 架构图（4 个 PEER Agent + 12 个 wp-* Skill）运行"的总体方案。

## 0. 一句话目标

让每一个该由 Skill 完成的动作，都【真正通过 invoke_skill 调用对应的 Skill】来完成，
而不是绕过 Skill 机制、用写死的 if/elif 直连底层服务。做完后，架构图（4 Agent + 12 Skill）
与真实代码一致，"这 12 个 Skill 真跑起来了吗"的答案是"是"。

## 2. 为什么这件事风险最高（要诚实）

前面 v3.8.1/.2 都能做到"前端零感知、行为零变化"，因为它们不碰执行流。**C 范围必然改变执行流**——把"直连服务"改成"经 invoke_skill 调"，中间多了一层调度。风险点：

1. **行为可能漂移**：同一个动作，直连 vs 经 Skill 调，返回结构、异常处理、调用时机可能有细微差别，导致最终输出变化 → 破坏"前端验收不回退"。
2. **性能可能退化**：invoke_skill 经过 SkillsLoader 调度，比直连多开销。当前已知端到端 ~35s 敏感，不能再退。
3. **llm_dispatch 类型没实现**：wp-reasoning 要走 Skill，但 SkillsLoader 对 llm_dispatch 当前直接抛 NotImplementedError（v3.0 就没做）。这是个真实的前置缺口，要先补机制。
4. **并行结构**：position 路由现在用 ThreadPoolExecutor 并行跑 check-discipline / generate-signals，改成经 Skill 调要保证并行不破。

**正因如此，C 范围必须用"双轨 + feature flag"**（这次是真要用上了，不像前几版）：每个 Skill 接通时，保留旧的直连路径作 fallback，新增"经 invoke_skill"路径，flag 切换，对账层验证两条路径输出一致后，再删旧路径。

## 3. 怎么拆成安全的小步（核心：一次一个 Skill）

**绝不一次性大改 4 个 Agent。** 按"从易到难、从低风险到高风险"逐个 Skill 接通，每步独立验收。建议顺序：

### 阶段一：机制补齐（不接任何 Skill，纯铺路）
- **C0**：补 SkillsLoader 的 llm_dispatch 支持（wp-reasoning 要用）。不接通任何 Skill，只让机制就绪 + 单测。

### 阶段二：低风险 Skill 先接（验证整套接通+验收范式跑得通）
- **C1**：wp-output-validator（Reviewing）—— validation 类型机制已支持，Reviewing 无并行无复杂分支，最干净，拿它趟路。
- **C2**：wp-retrieve-principles —— tool 实现已存在，只是把直连改成 invoke。general 路由的 Case 5 已是"对得上"的样板，风险低。

### 阶段三：中风险 Skill
- **C3**：wp-fetch-holdings —— 涉及 load-context 内部解耦，要把 data_loader 里 Step 2 抽出来变成真 invoke。
- **C4**：wp-fetch-research —— 同上 Step 7，且要统一 position/portfolio 两条路径。
- **C5**：wp-calc-allocation-deviation + wp-propose-allocation —— 让 portfolio 路径真 invoke 这俩（含 LLM Selector 增补真生效，这也是 v3.8.1 当初发现"Selector 是装饰品"的最终解药）。

### 阶段四：最高风险
- **C6**：wp-reasoning（Expressing）—— 依赖 C0，且 reasoning 是输出主体，行为漂移风险最大、最后做。含 6 个子函数（reason / reason_new_entry / review_portfolio / analyze_allocation / analyze_performance / chat）逐个接。

### 阶段五：收尾决策
- **C7**：收尾——删除所有 fallback 旧路径、退役 LEGACY 表、解除 SKILL_MANIFEST 的"不许读"限制
  让其正式驱动；将 citation-rules 的规范明确落入 reasoning prompt 文档。
  （citation-rules / action-planner 的归属已在 §4 拍定，C7 不再裁决，只做落实。）

每个 C 步都是一个独立小版本，走老节奏：勘探 → PRD → 实施 → 对账验收（验证"该 Skill 从绕过变成走通、且输出与旧路径一致"）→ 前端验收 → commit。

## 4. 两个不并入主流程的 Skill（已拍定）

PM 已决策，不留到 C7：

**wp-citation-rules —— 不作为独立可调度 Skill，归并为 wp-reasoning 的 prompt 规范。**
它是 prompt_inject 类型，本质是"给推理用的引用规范文本"，现状已硬编码进各 prompt 常量。
做成运行时 invoke 注入只会徒增复杂度。其"达标"形态 = 明确归入 wp-reasoning 的 prompt 规范，
不再视为需要单独接通的 Skill。

**wp-action-planner —— 承认为前端按钮触发的独立能力，不并入 PEER 主决策流程。**
它走的是"用户看完决策后点按钮生成行动计划"的独立交互，不在"提问→决策"主链路里。
架构图上标为"独立 Skill，前端直触"，这是诚实且合理的设计，不算"没接通"。

→ **主决策流程要接通的 Skill 明确为 10 个**：3 个已达标（load-context / check-discipline /
generate-signals）+ 7 个待改造（fetch-holdings / fetch-research / retrieve-principles /
output-validator / calc-allocation-deviation / propose-allocation / reasoning）。
citation-rules、action-planner 不计入主流程接通范围。

## 5. 已完成版本怎么处置（不浪费、不推翻）

- **v3.8.1 对账层**：留着，它是 C 范围每一步的验收工具——"这个 Skill 从绕过变成走通了吗"正是对账层能直接量出来的（invoked_not_declared 里那个 Skill 消失、matched 里出现，就是接通的标志）。
- **v3.8.2 SKILL_MANIFEST**：留着，它就是 C 范围的目标图纸。C 范围本质就是"让代码追上这张图纸"。届时解除"不许读"的限制，让 Agent 真按它驱动。
- **v3.8.2 LEGACY 表**：过渡兼容层，C 范围全部接通后退役。
- **v3.8.3 清幽灵**：⚠️ **取消/反转**。幽灵不删，改为在 C5 接通。这一版方向错了，停掉。
- **v3.8.4 小 bug**（action-planner 的 YAML 裸冒号）：action-planner 已定为前端直触、不并入主流程，
  但它仍需被 SkillsLoader 正常加载（前端触发也经 Skill 机制），所以这个 YAML bug 仍建议修，
  作为独立小补丁,不阻塞 C 范围主线。
