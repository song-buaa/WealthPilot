# v3.8 立项备忘: 意图编排层契约治理

**类型**: 架构重构
**前置**: v3.7（显性化清理 patch）合入
**预计工作量**: 待评估

## 主题清单

### 1. 完整 Planning-Executing 契约修复

让 ExecutingAgent 真消费 `PlanningOutput.selected_skills` 驱动执行，替代当前硬编码 if/elif route 分支。

### 2. _SKILL_BUNDLES_BY_ROUTE 结构升级

分阶段 dict（executing / expressing / reviewing），或更结构化的描述方式。当前扁平 list[str] 混合了三个 Agent 阶段的能力，语义不清。

### 3. 产品能力型幽灵 Skill 决策

`wp-calc-allocation-deviation` 和 `wp-propose-allocation` 从 v3.0 起存在于 bundle 配置和 LLM Selector 候选集中，但 ExecutingAgent 和 decision_service 任何路径都不调用。

这是**产品决策**（资产配置/再平衡能力要不要做），不是技术清理。

两个选项：
- **接通**: 在 portfolio 路由的 ExecutingAgent 中真实调用，实现资产配置偏离度计算和再平衡建议
- **清理**: 从 bundle 和 `_LLM_SELECTABLE_EXTRA_SKILLS` 中移除

### 4. 规范型/文档型 Skill 归属重新定义

`wp-citation-rules` 当前在 bundle 中但无 invoke 点。它可能本来就不应该被 invoke——其功能是作为 reasoning prompt 的输出规范被吸收，而不是作为独立可调用 Skill。

v3.8 需要决定：这类"规范型 Skill"是否应该归入 Skill 协议层，还是迁移为 prompt 模板的一部分。

**注意：此项与上一项（产品能力型）不同类，不要一刀切处理。**

### 5. LangGraph 残留清理

`backend/graph/tools.py` 中 `execute_retrieve_principles` 等已注册到 LangGraph tool dispatch 但 v3 PEER 管道不走 LangGraph 的死代码。

### 6. Direct Service 治理

市场数据服务（futu_quote / av_fundamentals / tiger_kline / futu_capital_flow）和 data_loader 内部行为（第 7b 步原则 RAG）是否要 Skill 化。当前这些能力由 ExecutingAgent 直接调用底层服务，绕过 Skill 层。

## 次要清理项 (carry-over from v3.7)

### wp-action-planner SKILL.md YAML 解析失败

- **文件**: `skills/wp-action-planner/SKILL.md`
- **问题**: description 字段含裸冒号 `trigger: manual_button_only` 导致 YAML 解析失败
- **影响**: `SkillsLoader.discover()` 静默跳过该 Skill，但 wp-action-planner 由前端按钮直接触发，不影响生产功能
- **修复方式**: description 字段值用引号包裹，或把 trigger 改为独立 YAML 字段
- **优先级**: 低（不影响功能）

### M5 回归脚本 API 参数名不兼容

- **文件**: `scripts/m5_e2e_18_cases.py`
- **问题**: 脚本使用 `session_id` 参数，但当前 API 期望 `conversation_id`，导致 18/18 全 0 字输出。该问题 v3.6 时代已存在，`docs/m5_e2e_report.md` 中已有记录。
- **影响**: M5 回归测试自 v3.6 起实际未真正运行；validators 跑了但 inputs 全空
- **修复方式**: 脚本里 `session_id` → `conversation_id`
- **优先级**: 中（影响回归测试能力恢复）
