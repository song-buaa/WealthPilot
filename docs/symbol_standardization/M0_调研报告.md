## 三、决策 / 投研模块 symbol 使用

### 3.1 决策引擎（PEER 主链路）

决策引擎 **不使用规范化 symbol**，全程使用 `asset_name`（中文名/自然语言名称）：

- `PlanningAgent`：从用户输入提取 `intent.asset`（如 `"理想汽车"`）
- `ExecutingAgent`：用 `asset_name` 匹配持仓、加载数据
- `ExpressingAgent`：输出 `structured_payload` 中无 symbol 字段

`decision_history` 表实际数据：
```
贵州茅台, 纳指100ETF, 广发纳指100ETF联接(QDII)C, 理想汽车
```

### 3.2 ExecutingAgent 的 ad-hoc symbol 构造

`backend/agents/executing_agent.py:292-306` 中存在 **硬编码的 ticker→wp_symbol 推断**：

```python
# 从持仓 ticker 推断 wp_symbol（用于市场数据查询）
if ticker.isdigit() and len(ticker) >= 4:
    wp_symbol = f"{ticker}.HK"
else:
    wp_symbol = f"{ticker}.US"
```

这里构造的是 `TICKER.MARKET`（点分隔）格式，传给 `fetch_quote()`。

### 3.3 market_data 层

market_data 各服务统一接收 `wp_symbol` 参数（`TICKER.MARKET` 格式）：

- `futu_quote_service`：`wp_symbol.rsplit(".", 1)` → 转成富途 `MARKET.TICKER` 格式
- `av_fundamentals_service`：`wp_symbol.rsplit(".", 1)` → 提取纯 ticker
- `tiger_kline_service`：`wp_symbol.rsplit(".", 1)` → 提取纯 ticker

### 3.4 投研模块

`research_service.py` 使用 `Symbol.parse()` 处理 `TICKER:MARKET`（冒号分隔，v2 格式），主要在 ViewpointCard 入库和查询时使用。

### 3.5 API 桥接层 _infer_symbol

`backend/api/research.py:312-351` 的 `_infer_symbol()` 函数是 **positions 表 → v2 格式** 的桥接：

```python
# ticker="00068", currency="HKD" → ("68:HK", "HK", True)  ← 注意去掉了前导零！
# ticker="AAPL", currency="USD" → ("AAPL:US", "US", True)
# ticker="600519.SH" → ("600519:SH", "SH", True)
```

**港股前导零处理不一致**：
- positions 表：`00068`（5 位补零）
- viewpoint_cards_v2：`700:HK`（去前导零，但不补零到 4 位）
- _infer_symbol：`lstrip("0")` 去掉所有前导零
- entity_registry.yaml：`0700:HK`（保留 1 个前导零到 4 位）

### 4.2 OrderRequest 契约（BrokerAdapter 抽象层）

```python
# backend/services/action/brokers/base.py:22
class OrderRequest:
    symbol: str  # US.LI / HK.03690 / CN.601318  ← MARKET.TICKER（点分隔，市场前缀）
```

这是 **第四种格式**：`MARKET.TICKER`（与富途 SDK 原生格式一致，与 broker_sync 归一化格式相反）。

### 4.3 TigerBrokerAdapter._parse_symbol

`backend/services/action/brokers/tiger.py:334-348` 实现了启发式解析，兼容带前缀和纯代码两种输入：

```python
@staticmethod
def _parse_symbol(symbol: str) -> tuple[str, str]:
    if "." in symbol:                    # "US.SPY" → ("US", "SPY")
        market, pure = symbol.split(".", 1)
        return market.upper(), pure
    if symbol.isdigit():
        if len(symbol) in (4, 5):        # "00700" → ("HK", "00700")
            return "HK", symbol
        if len(symbol) == 6:             # "600519" → ("CN", "600519")
            return "CN", symbol
    return "US", symbol                  # "MSFT" → ("US", "MSFT")
```

### 4.4 OrderManager → BrokerAdapter 的 symbol 传递

当前 `symbol_strategies.symbol` 直接传给 `OrderRequest.symbol`。但 symbol_strategies 存的可能是 `LI`（纯 ticker）或 `理想汽车`（中文名），而 `OrderRequest` 期望 `US.LI`（`MARKET.TICKER`）。**这个断裂在 Mock 环境下不会报错，但真实券商对接时会爆炸。**

### 4.5 order_records 表

```sql
CREATE TABLE order_records (
    symbol VARCHAR(50) NOT NULL,
);
```

实际数据：`LI`、`AAPL`（纯 ticker，与 symbol_strategies 一致）。

**没有全局统一的 normalize 函数**。每个模块各自实现，格式假设不同。

## 六-bis、前后端契约层 symbol 格式

### API 响应中 symbol 格式

| API 端点 | 返回字段 | 格式 |
|---------|---------|------|
| `/api/research/v2/holdings` | `symbol` | `TICKER:MARKET`（v2 格式，由 `_infer_symbol` 转换） |
| `/api/research/v2/cards` | `primary_symbol` | `TICKER:MARKET`（直接从 DB） |
| `/api/action/strategies` | `symbol` | 混乱（纯 ticker 或中文名，直接从 DB） |
| `/api/action/orders` | `symbol` | 纯 ticker |

### 前端 symbol 消费方式

前端 **没有对 symbol 做格式解析（split）**。主要消费模式：

1. **直接展示**：`strategy.symbol` / `card.facts.primary_symbol` 直接渲染到 UI
2. **传参查询**：`researchV2Api.queryCards({ symbol: v2SearchSymbol })` — 把 symbol 原样传回后端
3. **名称映射**：`h.asset_name.split(' (')[0]` — 只对 asset_name 做拆分，不对 symbol

**前端硬编码风险极低**。如果后端统一改格式，前端只需确保展示正确即可，不需要改解析逻辑。但 Action 模块的 `strategy.symbol` 显示（如展示 `理想汽车` 而非 `LI`）可能需要适配。

### 回归影响评估

- Research 页面：展示 `primary_symbol`，改格式后自动跟随，**无需改动**
- Action 页面：展示 `strategy.symbol`，当前展示中文名或 ticker 都有，改格式后可能影响用户感知但 **不会报错**
- Decision 页面：使用 `asset_name`（中文名），**完全不受影响**

## 八、关键发现 / 意外

### 发现 1：系统中实际存在 4 种 symbol 格式

| 格式 | 分隔符 | 顺序 | 使用者 |
|------|--------|------|--------|
| `TICKER:MARKET` | 冒号 | ticker 在前 | v2 投研模块、EntityRegistry、API _infer_symbol |
| `TICKER.MARKET` | 点 | ticker 在前 | broker_sync 归一化、market_data 查询、ExecutingAgent |
| `MARKET.TICKER` | 点 | market 在前 | OrderRequest 契约、富途 SDK 原生格式 |
| 纯 ticker | 无 | — | positions 表、symbol_strategies、order_records、LLM 输出 |

### 发现 2：港股代码补零策略完全不统一

| 位置 | 腾讯代码 | 补零策略 |
|------|---------|---------|
| 老虎 SDK 返回 | `700` | 不补零 |
| positions 表 | `00700`（推测） | 5 位补零（由 PositionUpsertService 处理） |
| broker_sync normalize | `00700.HK` | 5 位补零 |
| viewpoint_cards_v2 | `700:HK` | 不补零 |
| entity_registry.yaml | `0700:HK` | 4 位补零 |
| _infer_symbol | `700:HK`（从 `00700` lstrip 零） | 去掉所有前导零 |

**同一个标的在不同表中有 3 种写法**，跨表 JOIN 或匹配时必定出 bug。

### 发现 3：symbol_v2 字段已预留但从未被填充

`positions` 表已经添加了 `symbol_v2 TEXT` 列，但所有值为 NULL。说明之前可能已有统一 symbol 的计划但未执行。

### 发现 4：ActionPlanner LLM 输出的 symbol 完全不可控

prompt 模板只写 `"symbol": "标的代码"`，未指定格式。LLM 有时输出 `LI`，有时输出 `理想汽车`。这导致 symbol_strategies 表数据混乱，且与 OrderRequest 期望的 `MARKET.TICKER` 格式不兼容。

### 发现 5：decision_history 和 research_documents 使用中文名是刻意设计

这两个模块用 `asset_name` / `object_name` 存储中文名，是语义上的"标的名称"而非"标的代码"。不应被纳入 symbol 统一范围，但需要有 **名称 → symbol 的映射机制**。

### 发现 6：前端无格式硬编码风险

前端不解析 symbol 格式（不 split `:` 或 `.`），只做原样展示和传参。后端改格式对前端影响极小。

## 九、给 PM 的格式统一建议

### 方案 A：`<TICKER>:<MARKET>` — 遵循 v2（推荐）

格式：`LI:US`、`0700:HK`、`600519:SH`

**优点**：
- 已有 `Symbol` 类（`research_v2/symbol.py`）提供 parse/format/validate
- ViewpointCard 已落地，数据已存在（约 50+ 条）
- EntityRegistry 已基于该格式设计
- 冒号分隔符不会与任何券商 SDK 原生格式冲突
- `_infer_symbol()` 已输出该格式

**缺点**：
- broker_sync 层（`TICKER.MARKET`）需要改 3 个 Adapter
- market_data 层（`TICKER.MARKET`）需要改 4 个服务
- OrderRequest（`MARKET.TICKER`）需要改注释和 _parse_symbol

**改动量**：~15 个文件，涉及格式转换的约 ~30 处

### 方案 B：`<MARKET>.<TICKER>` — 遵循 v3.2 OrderRequest 注释

格式：`US.LI`、`HK.0700`、`SH.600519`

**优点**：
- 与富途 SDK 原生格式一致（`US.QQQ`）
- OrderRequest 已按该格式设计
- TigerBrokerAdapter._parse_symbol 已支持

**缺点**：
- 与 v2 投研模块全面冲突（ViewpointCard 50+ 条数据需迁移）
- 需要重写 `Symbol` 类或废弃
- 市场前缀在阅读时不直观（先看市场再看 ticker）
- 只有 OrderRequest 一处使用，实际数据库中 **无此格式的存量数据**

**改动量**：~20 个文件（v2 模块改动更多）

### 方案 C：`<TICKER>.<MARKET>` — broker_sync 现有格式

格式：`LI.US`、`00700.HK`、`600519.SH`

**优点**：
- broker_sync 层已全面使用，position_snapshots 有存量数据
- market_data 层已全面使用
- 与行业惯例接近（Yahoo Finance 用 `0700.HK`）

**缺点**：
- 与 v2 `Symbol` 类冲突（需改冒号为点）
- ViewpointCard 存量数据需迁移
- 点号分隔可能与某些 ticker 含点号的情况冲突（如 `BRK.B`）

**改动量**：~12 个文件

### 推荐：方案 A（`TICKER:MARKET`）

**理由**：
1. **已有最多正确落地的代码和数据**：Symbol 类、ViewpointCard、EntityRegistry、_infer_symbol
2. **冒号分隔避免与券商格式冲突**：不会与 `BRK.B` 等含点的 ticker 冲突
3. **向前兼容**：Entity 层设计已基于此格式
4. **改动方向清晰**：broker_sync/market_data 加一层薄转换即可
5. **LLM 友好**：冒号分隔在 prompt 中更容易向 LLM 解释（"ticker 冒号 market"）

**核心 trade-off**：broker_sync 和 market_data 两层需要改内部格式（或在边界处加转换函数），但这两层本身就有各自的 normalize 函数，加一个全局 `symbol_to_broker_sync()` / `symbol_from_broker_sync()` 即可。

## 十、PM 决策清单

### 1. 格式选型：A / B / C？

**推荐 A**（`TICKER:MARKET`）。理由见第九节。

如果选 B 或 C，需要额外迁移 ViewpointCard 存量数据和重写 Symbol 类，代价更高。

### 2. 港股代码补 0 策略：0700 还是 00700？

| 来源 | 腾讯代码 | 说明 |
|------|---------|------|
| 老虎 SDK 返回 | `700` | 不补零 |
| 富途 SDK 返回 | `00700` | 5 位补零 |
| 港交所官方 | `0700` | 4 位 |
| 当前 broker_sync | `00700` | zfill(5) |
| 当前 viewpoint_cards | `700` | 无统一规则 |
| entity_registry.yaml | `0700` | 4 位 |

**建议**：统一为 **4 位补零**（`0700`），与港交所官方一致。
- 规则：`ticker.zfill(4)`
- `700 → 0700`、`68 → 0068`、`9988 → 9988`（已 4 位无需补）
- 需修改 broker_sync 三个 Adapter（当前 zfill(5) → zfill(4)）和 _infer_symbol

### 3. A 股代码后缀：SH/SZ 还是 SS/SZ？

当前系统已使用 `SH`/`SZ`（`VALID_MARKETS = {"US", "HK", "SH", "SZ"}`）。

**建议维持 SH/SZ**。理由：
- 已有代码和数据使用此格式
- 与国内券商惯例一致
- Yahoo Finance 的 `SS` 是少数派

### 4. 历史数据迁移策略

| 表 | 数据量 | 迁移方式 |
|----|--------|---------|
| `positions.ticker` | ~200 行 | 填充 `symbol_v2` 列（已预留！） |
| `position_snapshots.symbol` | 按同步次数 | 加 `symbol_v2` 列或直接改 `symbol`（每次同步覆盖） |
| `viewpoint_cards_v2.primary_symbol` | ~50 行 | 仅需统一港股补零（`700:HK` → `0700:HK`） |
| `symbol_strategies.symbol` | ~10 行 | 需要人工审核 + 批量修正中文名 |
| `order_records.symbol` | ~5 行 | 需要补 `:MARKET` 后缀 |

**推荐**：
- **方案 4-A（推荐）：填充 `symbol_v2`，读取层优先用 `symbol_v2`**
  - 利用已预留的 `symbol_v2` 字段
  - 写一个迁移脚本填充：`ticker` + `currency` → `TICKER:MARKET`
  - 读取层改为 `symbol_v2 or ticker` fallback
  - 优点：零风险、可回滚、不影响现有逻辑

- 方案 4-B：全量改写 DB
  - positions 表加 `symbol` 和 `market` 字段，一次性填充
  - 删除 `ticker` 字段（或保留但停止使用）
  - 优点：彻底干净
  - 缺点：需要改所有查询 positions.ticker 的代码

### 5. Entity 层是否同步重做？

**建议：本专项不做 Entity 层，单独立项。**

理由：
- EntityRegistry 是增强层（跨市场聚合），不是核心功能
- 当前 entity_registry.yaml 仅 9 个实体，属于草稿
- `primary_entity_id` 字段全部为空，说明从未真正使用
- Symbol 统一是 Entity 层的前置依赖，先做好 Symbol 再做 Entity

### 6. TigerBrokerAdapter._parse_symbol 简化预判

**专项完成后可以大幅简化但不能变成纯 split。**

原因：
- 统一格式后，OrderRequest.symbol 将始终是 `TICKER:MARKET`（如 `LI:US`）
- `_parse_symbol` 可简化为 `symbol.split(":", 1)` → `(market, ticker)`
- 但 **反向映射**（`TICKER:MARKET` → Tiger SDK 格式）仍需要：
  - 港股：`0700:HK` → Tiger API 需要纯 ticker `0700` 或 `00700`
  - A 股：`600519:SH` → Tiger API 需要的格式待确认
- 建议在 M1 阶段验证 Tiger SDK 对各市场的 ticker 输入要求

### 附加问题 7：ActionPlanner prompt 应明确 symbol 格式

当前 prompt 只写 `"symbol": "标的代码"`。需要改为：

```
"symbol": "标的代码，格式为 TICKER:MARKET（如 LI:US、0700:HK、600519:SH）"
```

并在 `_parse_draft_response()` 中加入 symbol 格式校验（检查是否包含 `:`）。

### 附加问题 8：`_infer_symbol` 的港股补零 bug

当前 `_infer_symbol` 用 `lstrip("0")` 去掉所有前导零，导致 `00068` 变成 `68:HK`。如果统一为 4 位补零，需要改为 `lstrip("0").zfill(4)` → `0068:HK`。
