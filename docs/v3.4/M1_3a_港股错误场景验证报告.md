## 2. 每个场景的详细记录

### 场景 1: 港股 BUY 挂单 -> HELD

place_order 返回:
- status: `submitted_to_broker`
- broker_order_id: `43208121682380800`
- tiger_status: `OrderStatus.NEW`
- raw_response 完整(含 broker/account_type/market/currency/outside_rth 等 §4.1 全部字段)

3 秒后 get_order_status:
- status: `broker_pending`
- tiger_status: `OrderStatus.HELD`
- filled_quantity: 0

**与 M1.2 单测预期对比**: 完全一致。place_order 返回时 Tiger 侧状态是 NEW(mapped -> submitted_to_broker),几秒后变为 HELD(mapped -> broker_pending)。

### 场景 2: 港股 BUY 撤单 -> CANCELLED

- cancel_order 返回: `True`
- 撤单后立即查: status = `cancelled`, tiger_status = `OrderStatus.CANCELLED`
- 3 秒后再查: status 稳定为 `cancelled`
- reason 字段: `None`(撤单成功无 reason)

**与 M0 笔记对比**: 一致。撤单是同步的,cancel_order 返回后 status 立即变为 CANCELLED。

### 场景 3: 超额单 -> EXPIRED -> rejected

**这是 M0 发现的最大意外的正式验证。**

- place_order 立即返回 `submitted_to_broker`(Tiger 先接受挂单)
- 5 秒后 get_order_status:
  - tiger_status: `OrderStatus.EXPIRED`
  - reason: `"您的可用资金或者可用购买力不足"`
  - mapped_status: `rejected`(经 _map_expired 关键词匹配"购买力")
  - expired_resolved_as: `rejected`

**验证结论**: M1.2 的 EXPIRED 二义性映射逻辑**完全正确**。Tiger 超额单不走 REJECTED 而走 EXPIRED,reason 关键词"购买力"被 _map_expired 正确捕获并映射为 rejected。

### 场景 4: 不存在 symbol -> rejected

- place_order 返回: status = `rejected`
- raw_error_code: `1200`
- raw_error_message: `"code=1200 msg=standard account response error(bad_request:合约不正确)"`
- 错误消息含 "合约" 和 "bad_request",`unknown_api_error` 标记**未出现**(正确: 已知错误类型)

**与 M0 笔记对比**: 一致。不存在 symbol 在 place_order 阶段直接抛 ApiException。

### 场景 5: not_found -> OrphanOrderError

**偏差发现**:

预期: Tiger 返回 `not_found:订单不存在`(code=1200),触发 _get_order_with_retry 的 not_found 检测。

实际: Tiger 返回 `code=1010 msg=biz param error(failed to parse parameters in 'biz_content')`。

原因: 测试用的 broker_order_id `"9999999999999999999"` 超出了 Tiger 服务端的整数解析范围(int64 溢出),Tiger 在参数层就拒绝了,没进入订单查询逻辑。

**影响分析**:
- M1.2 的 not_found 重试逻辑本身没有 bug,只是本次测试用的 fake ID 触发了不同的错误路径
- code=1010 不含 "not_found" 关键词,所以没触发重试,直接走了 `except ApiException` 兜底返回 unknown
- **真实场景中** not_found 只会发生在"刚 place_order 返回了 broker_order_id 但 Tiger 端还没同步"的极端窗口,M1.3b 美股开盘时段可以用真实的已撤单 order_id 补测

**功能判定**: PASS(兜底路径正常工作,not_found 重试路径待 M1.3b 补测)

## 3. 与 M0 笔记 + M1.2 单测的对比

### 一致的部分
- broker_order_id 确实在 `order.id` 字段(int -> str)
- 挂单后 Tiger 状态变化: NEW -> HELD
- 撤单同步: cancel_order 后立即 CANCELLED
- 超额单: EXPIRED + 购买力关键词 -> rejected 映射正确
- 不存在 symbol: ApiException code=1200 "合约不正确"
- place_order 返回时 tiger_status 是 `OrderStatus.NEW`(不是 HELD),M1.2 映射表中 NEW -> "submitted_to_broker" 正确

### 偏差
1. **场景 5 not_found 路径**: 超大 broker_order_id 触发的是参数解析错误(code=1010)而非 not_found(code=1200)。需要 M1.3b 用真实 order_id 补测。
2. **place_order raw_response 中 tiger_status 格式**: 实际是 `"OrderStatus.NEW"` 字符串(包含枚举类名前缀),M1.2 单测中 mock 的 `str(TigerOrderStatus.HELD)` 也是这个格式,所以一致,但 UI 层展示时需要注意去掉前缀。
