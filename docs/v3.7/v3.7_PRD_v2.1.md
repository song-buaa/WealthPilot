# WealthPilot v3.7 PRD v2.0: 意图编排层显性化清理

**版本**: v3.7  
**PRD 版本**: v2.1（终稿）  
**类型**: 架构清理 Patch（不是重构）  
**主题**: 显性清理 + 显性标注，不做治理  
**风险等级**: 极低  
**预计工作量**: 0.5-1 天

---

## 0. 版本定位（核心边界）

**v3.7 只做"显性清理 + 显性标注"，不做"能力接通 / 能力弃用 / 契约重构"。**

具体边界：

| 做 | 不做 |
|---|---|
| 删确定无用的死文档 | 改任何执行逻辑 |
| 修确定错误的文档描述 | 重构 bundle 数据结构 |
| 加注释让"幽灵 Skill"显性化 | 决定幽灵 Skill 接通或弃用 |
| 加日志让契约断裂显性化 | 修复契约断裂 |
| 加日志让 v3.6 半接通显性化 | 修复 v3.6 半接通 |

凡是涉及"这个能力未来要不要做、要不要接通、要不要移除"的决策，全部留给 v3.8。v3.7 的价值是**把坑暴露出来，不是今天填坑**。

## 1. 任务背景与目标

### 1.1 立项触发

v3.0 PEER + Skills 架构落地至今（v3.6），意图编排层累积了多项概念/配置/代码不一致。这些不一致在功能层面不阻塞用户，但会持续误导未来读者和后续演进。v3.7 用一个最小化的清理版本，让"明确是错的"被修正，"暂时不确定的"被显性标注，为 v3.8 真正的契约重构提供干净起点。

### 1.2 勘探发现的三类不一致

经过三轮代码勘探，确认当前存在以下不一致：

#### 不一致 1：文档死代码

`skills/wealthpilot-position-decision/SKILL.md` 是 v3.0 时期写的"意图级 SOP 文档"，但在整个运行时不被任何组件读取（不在 `_SKILL_BUNDLES_BY_ROUTE`、不在 `_LLM_SELECTABLE_EXTRA_SKILLS`、ExecutingAgent 不解析）。其同目录的 `references/` 和 `scripts/` 子文件也是死代码。

它的存在带来概念混乱：与 12 个原子能力 Skill 并列放在 `skills/` 目录下，但实际定位完全不同（前者是 workflow 编排描述，后者是原子能力），导致 README、AGENTS.md 等文档对"Skills 协议层"的描述前后矛盾。

#### 不一致 2：Planning-Executing 契约断裂

`PlanningOutput.selected_skills` 字段（含 LLM Skill Selector 增补的结果）在下游 ExecutingAgent 中零读取——ExecutingAgent 按 `route` 做硬编码 `if/elif` 分支，完全不消费 PlanningAgent 算出的 Skill 清单。

后果：LLM Skill Selector 从 v3.0 引入至今是装饰品。增补的 extra_skills 只进日志和评测字段，不影响实际执行。

#### 不一致 3：配置漂移与"幽灵 Skill"

`_SKILL_BUNDLES_BY_ROUTE` 配置与 ExecutingAgent 实际执行清单存在多处偏离，特别是发现两类"幽灵 Skill"——存在于配置中但无任何代码路径调用：

| Skill | 出现在 | 实际调用 |
|---|---|---|
| wp-retrieve-principles（position/portfolio 路由） | bundle | data_loader 内部触发，但 LLM 不消费（v3.6 半接通） |
| wp-calc-allocation-deviation | bundle + LLM Selector 候选集 | 任何路径都不调用（v3.0 起的幽灵） |
| wp-propose-allocation | bundle + LLM Selector 候选集 | 任何路径都不调用（v3.0 起的幽灵） |

这些幽灵 Skill 的处理涉及产品决策（资产配置能力要不要做），不是 v3.7 能解决的范围。

### 1.3 v3.7 核心目标

用一个最小化、低风险的版本处理上述三类不一致中"明确可清理"和"必须显性化"的部分。具体：

1. 删除确定无用的文档死代码（不一致 1）
2. 让契约断裂可观测（不一致 2）—— 加日志，不修
3. 让幽灵 Skill 和配置漂移显性标注（不一致 3）—— 加注释，不动结构

### 1.4 明确排除的范围（工程纪律）

v3.7 **不做**以下事情：

- **不重构 `_SKILL_BUNDLES_BY_ROUTE` 数据结构**：保持现有 `dict[str, list[str]]` 不变。分阶段 dict、PEER 四层对齐结构等设计归 v3.8
- **不修 ExecutingAgent 真正消费 `selected_skills` 的契约**：v3.8 重构主线
- **不修 `wp-retrieve-principles` 的 LLM 注入断点**：涉及 prompt 工程 + L3 评测基线重建，独立 v3.6.5 patch 处理
- **不决定幽灵 Skill 的去留**：`wp-calc-allocation-deviation` / `wp-propose-allocation` 保留现状，仅加 TODO 注释。v3.8 统一决策
- **不清理 LangGraph 残留**（`execute_retrieve_principles` 注册到 LangGraph 但 v3 PEER 不走 LangGraph）：v3.8 LangGraph 残留主题
- **不引入"data_loader 阶段"等新的配置维度**：保持 bundle 是 list[str]，避免扩大模型

### 1.5 v3.7 命题陈述

> **v3.7 是一次"显性化 patch"。它不引入新能力、不修复用户感知功能、不改变任何执行行为，也不重构数据结构。它的唯一价值是：让"明确的错"被修正、"暂时的迷"被注解清楚。这是为 v3.8 真正的契约重构准备一个干净的起点。**

## 3. 改造方案与设计决策

### 3.1 改造范围

v3.7 包含且只包含以下 4 类改动：

1. **删除死代码**：`skills/wealthpilot-position-decision/` 整个目录
2. **修正文档**：`README.md` + `AGENTS.md` 中明确错误的描述
3. **注释显性化**：`_SKILL_BUNDLES_BY_ROUTE` 上方加注释说明语义边界 + 对幽灵 Skill 加 TODO(v3.8)
4. **日志显性化**：两类显性化日志（契约不驱动 + 半接通状态）

### 3.2 关键设计决策

#### 决策 1：保持 `_SKILL_BUNDLES_BY_ROUTE` 结构不变

继续使用 `dict[str, list[str]]` 扁平结构，不重构为分阶段 dict。

**为什么**：
- 结构升级会牵动 `PlanningOutput.selected_skills` schema、`test_planning_agent.py` 和 `test_contracts.py` 断言、planning_agent 内部赋值逻辑
- 即使勘探证实下游对 selected_skills 零读取，结构改造仍是"不必要的扰动"——v3.7 目标是稳定的清理，不是干净的重构
- 真正的分阶段契约结构是 v3.8 的核心议题之一，届时联合 ExecutingAgent 真消费 selected_skills 一起重构更合理

#### 决策 2：以"注释"代替"配置改动"

不修改 bundle 内容，而是在配置文件加注释明确语义边界。

**为什么**：
- bundle 当前包含 ExpressingAgent / ReviewingAgent 阶段的能力（wp-reasoning / wp-citation-rules / wp-output-validator），从严格 ExecutingAgent 契约角度是"不一致"，但从"完整意图能力清单"角度又是合理的
- v3.7 不决定"bundle 到底应该表达什么"——这是 v3.8 重构议题
- 用注释说明"当前 bundle 不是 ExecutingAgent 执行契约，仅为 PlanningOutput 和 LLM Selector 提供候选参考"，比改动配置更安全

#### 决策 3：幽灵 Skill 保留现状 + TODO 标注

`wp-calc-allocation-deviation` 和 `wp-propose-allocation` 不从 bundle 和 LLM Selector 候选集中移除。

**为什么**：
- 它们是否应该真正接通涉及产品决策（资产配置 / 再平衡能力要不要做），不是技术清理范畴
- 即使移除，LLM Selector 双重白名单保证不会被误增补回来，所以保留不会产生副作用
- v3.8 统一决策"接通真实能力 / 从配置清理"二选一，比 v3.7 仓促做产品决策更合理

#### 决策 4：契约日志只做"显性化"，不做"对比"

之前讨论过对比 `planned_executing_skills` vs `actual_invoke_skill_calls`。v3.7 不做这种细粒度对比，只加一条"selected_skills 不驱动执行"的提醒日志。

**为什么**：
- 细粒度对比需要在 ExecutingAgent 里定义 `_ACTUAL_SKILLS` 常量，这又是个"小重构"
- 当前事实是"selected_skills 完全不驱动执行"——这条事实比"差异有多大"更重要
- 提醒日志足够让 v3.8 决策时知道这个契约断裂存在，不需要量化数据

#### 决策 5：v3.6 半接通独立处理

`wp-retrieve-principles` 在 position/portfolio 路由下"召回到但 LLM 不消费"的半接通问题不在 v3.7 修复，独立立项 v3.6.5 patch。

**理由**（这是 PRD 的核心工程纪律展示）：

> **工程纪律：一个版本一个主题**
> 
> 勘探发现 v3.6 引入 wp-retrieve-principles 时数据流半接通——data_loader 召回 ✅、explain API 序列化 ✅、前端 KnowledgeCitations 展示 ✅，但 llm_engine.reason() 不消费 retrieved_principles 字段，导致 position/portfolio 路由下"用户看到的知识引用卡片"和"LLM 实际推理依据"脱节。
> 
> 这是真实 bug，但它的修复有两个特点决定了不应混进 v3.7：
> 
> 1. **修复涉及 LLM prompt 工程**：在 reason() 中加入 principles 注入会改变 18 个回归用例的所有 LLM 输出（至少多一段引用），需要重新校准 L3 LLM-as-judge 5 维度评分基线
> 2. **质量提升判定困难**：分数变化可能是真改善、可能是输出变长导致的虚假提升、可能某些 case 决策档位从 HOLD 变 REDUCE——需要逐 case 人工审核才能确认改进方向
> 
> 这种"修复+评测基线重建"的组合工作量与 v3.7 "显性化清理"定位完全不匹配。混入会导致 v3.7 主题散乱、风险炸开。
> 
> 正确处理：v3.7 加一条"retrieved_principles 半接通状态日志"，记录召回非空事实，为 v3.6.5 patch 提供量化基线。v3.6.5 patch 基于这些数据独立处理 prompt 注入 + 评测基线重建。
> 
> **一个版本只做一件事，是工程稳定性的基础。**

#### 4.1 LLM Selector 增补未生效日志

**触发条件**：仅在 LLM Selector 实际增补了 extra_skills 时触发（不是每次决策都触发）。

**为什么不每次都打**：每次决策都 warning 会变成背景噪音淹没真正的问题。真正有观测价值的场景是"LLM Selector 算了一些 extra skill 但实际不会执行"，这才是契约断裂的具体表现。

**实现方式**：在 `PlanningAgent.run()` 中 `_llm_augment_skills()` 返回 extra_skills 后判断：

```python
# v3.7: 显性化日志 —— LLM Selector 增补未生效
# 仅在 LLM Selector 实际增补了 skill 时触发，避免日志噪音
if extra_skills:
    logger.warning(
        f"[PlanningAgent] LLM Selector 增补了 {len(extra_skills)} 个 extra skills "
        f"但 ExecutingAgent 当前不消费 selected_skills，增补未实际生效。"
        f"route={out.route}, extra_skills={extra_skills}"
        f"（v3.8 将统一修复 Planning-Executing 契约）"
    )
```
